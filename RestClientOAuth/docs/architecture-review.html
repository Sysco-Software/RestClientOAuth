Multi-app workspace: core OAuth library · endpoint adapter · advanced redirect · examples
Version 1.0.0.0 (Unreleased)
Platform BC 28 / Runtime 17
Scope 4 apps
Findings 5
Overview

The codebase has undergone a rigorous redesign centred on three axes: (1) splitting the public-client token path from the confidential-client path via an OAuth Client KFM interface and OAuthClientType enum dispatch; (2) adding a Device Code flow as a third authorisation grant; (3) decoupling the core OAuth library from the endpoint adapter app, making the endpoint app optional. The overall pattern is interface → facade codeunit → internal impl codeunit throughout.

What's New in the Redesign
  • Added OAuth Public Client (OAuthPublicClientImpl) — new codeunit 50330 implements AcquireTokenByAuthorizationCode (with PKCE verifier), AcquireTokenByRefreshToken, and the new AcquireDeviceAuthorization / AcquireTokenByDeviceCode calls. Public client requests never attach a secret or certificate assertion.
  • Added Device Code Flow — codeunits 50326–50327 and a new Device Code Authorization page handle the polling loop, error propagation (authorization_pending, slow_down, expired_token), refresh-token reuse, and cancellation. Always uses the public client.
  • New OAuth Client KFM interface + OAuthClientType enum — Auth Code Grant flow now dispatches to public or confidential client at runtime via OAuthClient := OAuthClientType;. Selection is driven by the endpoint's OAuth Client Type configuration field, not by whether credentials happen to be present.
  • Changed App split — core vs endpoint adapter — Rest Client OAuth no longer depends on endpoint records. Rest Client OAuth Endpoints is a separate optional app that bridges generic Http Endpoint KFM records to the core OAuth objects. Domain apps can depend on the core app directly.
  • Changed Auth Code Grant flow supports public + confidential exchange — previously confidential only; now both paths live behind the OAuth Client KFM interface. Confidential still sends secret or signed JWT assertion; public sends verifier code only.
  • Added RedirectURINone — explicit no-op redirect URI implementation. Flow logic defaults None → Built-in during Auth Code acquisition so this sentinel value cannot cause a silent empty-code exchange.

Facade pattern

Interface → Facade → Impl

Every external codeunit delegates entirely to an Access = Internal impl. Public API is stable; impl can change independently.

Enum dispatch

Polymorphism via enum

OAuthAuthorizationFlowType, OAuthClientType, RedirectURIType, and OAuthAuthority enums implement their respective interfaces — concrete codeunit selected at value assignment.

Token lifecycle

In-memory only

Tokens live as SecretText on the flow codeunit. IsValid() compares ExpiresAt to CurrentDateTime. No persistent cache; re-auth on object disposal.

Architectural Strengths
✓
SecretText throughout — all tokens, secrets, and cert private keys are SecretText; never plain Text
✓
PKCE + state enforced — code_challenge_method=S256 and a CreateGuid() state parameter on every Auth Code request
✓
offline_access auto-added — both Auth Code and Device Code flows inject the scope before building the token request, preventing silent refresh failures
✓
Clean public/confidential split — OAuthClientType enum dispatch at the flow level; Device Code is always public, Client Credentials is always confidential
✓
Certificate → JWT assertion — confidential client builds a proper RS256 JWT client assertion from cert; reduces secret distribution risk
✓
App split is clean — core app has zero dependency on endpoint records; endpoint app is a pure adapter; domain apps can depend on core directly
✓
Extensibility preserved — OAuth Authority, OAuth Authorization Flow, and Redirect URI enums are all Extensible = true
✓
Refresh-first strategy — all flows prefer silent refresh over re-interaction; Client Credentials correctly skips refresh (never issued)
✓
NoImplicitWith + Cloud target — app.json enforces modern AL compile features; no legacy implicit with references

Finding Details
F1 — Critical Hardcoded credentials in example source Security
In BCConnectorWithSecret.Codeunit.al, CreateOAuthClientApplication() sets:

OAuthClientApplication.SetClientId('<YOUR_CLIENT_ID>');
OAuthClientApplication.SetClientSecret(SecretStrSubstNo('<YOUR_CLIENT_SECRET>'));

These look like real Azure AD credentials. If they are active they must be revoked immediately. Even if revoked, they set a dangerous precedent: consumers reading the example will copy the pattern and commit their own real credentials. The security documentation itself states "Secrets should be rotated and never committed to source control."
Fix: Replace with obviously fake placeholder values (e.g. '<your-client-id>'), or better, load them at runtime from EnvironmentInformation / Isolated Storage / a setup page — and add a comment explaining this explicitly.
F2 — High PKCE code verifier uses non-CSPRNG Security
GetPKCECodeChallenge() builds the 128-character verifier using Randomize() + Random(StrLen(AllowedChars)) in a loop. AL's Randomize() / Random() is a deterministic PRNG seeded from the clock. A predictable verifier degrades the PKCE guarantee: an attacker who can observe the authorization code and approximate the acquisition time can enumerate likely verifiers and attempt a token exchange.
Fix: Generate the verifier using CryptographyManagement.GenerateRandomBytes() (or equivalent) to get 32+ cryptographically random bytes, then Base64Url-encode them. Derive the challenge from that verifier with the existing SHA-256 + Base64Url logic.
F3 — Medium GetUrlEncodedScopes() does not URL-encode Correctness
The method joins scopes with a space character and trims the result. This output is used in two contexts:
  • POST body (application/x-www-form-urlencoded in token requests) — spaces should be encoded as + or %20 per RFC 1866.
  • URL query string (MicrosoftEntraIDImpl.GetAuthorizationEndpoint()) — spaces in a URI query component must be percent-encoded per RFC 3986. A raw space makes the URL technically malformed.
In practice Microsoft Entra accepts unencoded spaces in many contexts, so this is not a breaking bug today, but the method name is a false contract and a future authority implementation could fail on it.
Fix: Either rename to GetScopesAsText() / GetSpaceDelimitedScopes() and have callers encode as needed, or apply .Replace(' ', '%20') inside the method and honour the existing name.
F4 — Medium SetScopes() is additive, not a replacement Correctness
The implementation iterates ScopesList and calls Scopes.Add() for each entry. It does not clear the existing list first. Given that MicrosoftEntraIDImpl.GetApplicationConfig() calls SetScopes(ScopesList) after the config has already been populated from the app registration record, and offline_access is auto-added later by the flow, calling SetScopes on a non-empty config silently duplicates every scope. Duplicate scopes in a token request are tolerated by Entra but can cause unexpected scope claim expansion.
Fix: Clear the internal list at the top of SetScopes: Clear(Scopes); before the iteration. This makes the method behave as its name implies.
F5 — Low Asymmetric error handling: confidential vs public client Consistency
OAuthPublicClientImpl parses error and error_description from the JSON response body and surfaces them in a structured error label (TokenRequestErr). OAuthConfidentialClientImpl calls Error(ErrorInfo.Create(HttpResponseMessage.GetErrorMessage(), true)) directly — the OAuth error body is never read. When a confidential client token request fails (e.g., expired secret, wrong audience, certificate mismatch), the error message shown to the user is the HTTP-level status phrase rather than the specific OAuth error code.
Fix: Extract and propagate error / error_description in OAuthConfidentialClientImpl.SendTokenRequest(), mirroring the pattern in OAuthPublicClientImpl.
